# 07 故障注入、原生证据链与复盘

> 前置：`06-声明式管理与GitOps.md`。有了 Git 声明的期望状态，「什么叫偏离」才第一次有客观参照。本阶段在同一套 SOP 上跑三类故障。

## 架构与数据流

```
改 values → helm template 重渲染 → git commit / push → ArgoCD 同步（偏离生效）
        │
        v
只用原生信号定位：get events / describe pod / logs --previous / get endpoints
        │
        v
git revert --no-edit HEAD → push → ArgoCD 回到基线（证据链闭合）
```

- 三次故障都改 values 重渲染后注入 Git，`selfHeal` 不会来抢戏——偏离本身就是 Git 的期望状态。
- `git revert` 反的是 **diff** 不是 commit message：它生成一笔反向改动的新提交，历史保留，适合「留痕 + 可审计」的回滚。
- 原生信号分两层：**控制面信号**（events / describe / status）说明 K8s 认为发生了什么；**应用信号**（logs / Last State）说明进程实际发生了什么。两者不一致时，往往就是「全绿假象」。

## 三类故障与判据

**① 镜像 tag 不存在 → `ImagePullBackOff`**

```
sed -i 's#tag: "1.27"#tag: "1.27-not-exist"#' chart/nginx-demo/values.yaml
helm template nginx-demo ./nginx-chart --namespace gitops-lab > manifests/all.yaml
git add chart/ manifests/all.yaml && git commit -m "fault: bad image tag" && git push origin main
kubectl -n gitops-lab get pods -o wide
kubectl -n gitops-lab describe pod <pod> | tail -40
kubectl -n gitops-lab get events --sort-by=.lastTimestamp | tail -20
git revert --no-edit HEAD && git push origin main
```

判据：`describe` 的 Events 出现 `Failed to pull image` / `not found`；`STATUS` 为 `ImagePullBackOff`。注意 `crictl images` 里没有该镜像不等于故障原因，要先确认镜像缓存落在哪个节点（`get pods -o wide` 的 NODE 列）。

**② 坏 directive → `CrashLoopBackOff`**

```
sed -i 's#nginxArgs: daemon off;#nginxArgs: daemon off; bad_directive;#' chart/nginx-demo/values.yaml
kubectl -n gitops-lab logs <pod> --previous       # 上一次容器退出前的日志
kubectl -n gitops-lab describe pod <pod> | grep -A5 "Last State"
```

判据：`logs --previous` 出现 nginx 配置解析错误；`RESTARTS` 递增；`Last State: Terminated` 且 `Exit Code` 非 0。`CrashLoopBackOff` 与 `ImagePullBackOff` 的分界是「镜像拉到了但起不来」vs「镜像根本没拉到」。

**③ Service selector 写错 → 全绿假象**

```
sed -i 's#serviceSelector: nginx-demo#serviceSelector: nginx-demo-broken#' chart/nginx-demo/values.yaml
kubectl -n gitops-lab get pods -o wide            # 全 Running
kubectl -n gitops-lab get application ...          # Synced / Healthy
kubectl -n gitops-lab get endpoints nginx-demo     # subsets 为空 ← 唯一真判据
```

这是三类中唯一「所有仪表都绿但服务不可用」的：Pod、Deployment、Application 全正常，因为 selector 不匹配只影响 Service 的后端列表。判据必须落到 `endpoints` 的 `subsets`，不能靠 `get pods` 或 ArgoCD 状态。

## SLI / SLO 三问（复盘结论）

- **成功率怎么测**：手动 curl，测一次是一次，是**快照**不是历史。
- **恢复怎么判**：只有事件时刻，没有断流区间，MTTR 没有原始依据。
- **判不了达标**：`99%` 这类目标需要窗口聚合，靠人记几次 curl 无法对账。

这三条是 `08` 观测线的需求来源：需求文档定义的是**判定语义**（什么叫可用、窗口多长、按什么维度聚合、一次失败算不算失败），指标名是实现层「拿哪根现成的尺去量」的选择结果，Grafana 面板只存呈现定义、最不值钱。

## 已知坑与警示

- **把「全绿」当「可用」**：`get pods` / ArgoCD `Healthy` 都不检查 Service 后端是否有地址。selector 类故障必须查 `endpoints`。

- **凭 `crictl images` 判断镜像不存在**：镜像缓存在 Pod 所在的那个节点上，且 `imagePullPolicy: Always` 在离线环境会强制联网报到，即使本地有镜像也会 `ImagePullBackOff`。这两件事叠加时，「镜像到底在不在」的结论会完全反转（见 `08` 开机三案）。

- **把 `git revert` 当「撤销那次提交」**：revert 反的是 diff，生成新提交；历史里的故障提交仍在。要「抹掉历史」是另一回事，且会破坏证据链。

- **在错误的目录改 values**：教学 chart 与 GitOps chart 是两个目录（`/root/soft/demo-chart` vs `/root/gitops-work/chart/nginx-demo`）。改错目录时 `git diff` 只会显示无关文件或干脆为空，渲染产物不变。

- **故障注入不留截图**：`ImagePullBackOff` / `CrashLoopBackOff` 这类状态事后补不回来，动手前先确认截图点。

- **清单位置**：`k8s/gitops/`（nginx-demo chart 与 values）、`assets/screenshots/symptom-*`。故障复盘正文「报错原文 → 根因 → 解决 → 教训」采用四段式，不放主观叙事。
